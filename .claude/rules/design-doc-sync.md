# 設計書 ↔ 実装 同期ルール

## 原則

`不動産スクレイピングアプリ設計.md` は、アーキテクチャ（スクレイピング基盤・DBスキーマ・通知設計・分析メトリクス）の SSoT（Single Source of Truth）である。実装はこの設計書の内容と乖離してはならない。

ただし設計書は「現時点で最良の作業仮説」であり、実装を進める中で矛盾・陳腐化・実装困難さに気づくことは正常である。そのときに無断でどちらかに合わせて書き換えるのではなく、ユーザーに報告し、設計書を変更するか実装で吸収するかの合意を得る。

## トリガー

- `不動産スクレイピングアプリ設計.md` に差分があるコミット/PRを扱うとき
- 設計書に記載のあるコンポーネント（スクレイパー、DBスキーマ、通知モジュール、分析バッチ）の実装に着手する前
- 実装中に設計書の記述と矛盾する事実（ライブラリの制約、対象サイトの実際の挙動等）を発見したとき

## 見直し観点

| 設計書側の節 | 点検対象 |
|---|---|
| サーバーレス・スクレイピング基盤のインフラ設計 | スクレイパーの実行環境・コンテナ設定・タイムアウト |
| ボット検知の回避とステルス実装の技術的考察 | スクレイパーの振る舞い（レート制御を主とし、偽装は最小限に留めているか） |
| データレイクハウスとSCD Type 2 | DBスキーマ・マイグレーション・履歴保存ロジック |
| 希望物件の通知システム設計とレジリエンス | 通知モジュールの重複排除・リトライ・キュー設計 |
| 不動産データ分析と投資メトリクスの抽出 | 分析バッチのメトリクス算出ロジック（空室率・DOM等） |

## 乖離を発見したときの対応

1. 設計書の該当箇所（見出し・段落）を明示した上でユーザーに報告する。
2. 設計書と実装のどちらを正として揃えるかをユーザーに確認する（無断でどちらかに合わせて書き換えない）。
3. `.claude/rules/pr-judgment-request.md` の書式に従って報告する。
