# ユーザーへの判断要請ルール

## 原則

ユーザーに判断を仰ぐとき、**判断に必要な材料をすべて同じ場所に置く**。設計書の見出し名を書くことは根拠の提示であって、説明ではない。ユーザーが「設計書の該当箇所を読みに行かないと判断できない」状態で問いを投げてはならない。

判断を仰ぐことと、判断を丸投げすることは違う。**必ず自分の推奨案を先に述べ**、その上で異論の余地がどこにあるかを示す。

## トリガー

- 設計書と実装の乖離報告（`design-doc-sync.md` と併せて適用）
- 複数の選択肢を提示して選んでもらうとき
- 「安全側に倒した」判断の報告（法的リスク・データ破損リスクを避けるための選択）

## 必須要素（各項目に5つすべて）

| # | 要素 | 内容 |
|---|------|------|
| 1 | 何をしているか | 実装の事実。`ファイル名 行番号` を添える |
| 2 | 用語の補足 | 専門用語は初出時に1〜2文で噛み砕く（SCD Type 2、指数バックオフ等） |
| 3 | なぜそうしたか | 却下した代替案と、それを採った場合に具体的に何が壊れるか |
| 4 | 倒れる方向 | 失敗時にどちら側へ倒れるか（安全側／危険側） |
| 5 | 判断の要否 | 実際に返答が要る項目と、報告だけで足りる項目を視覚的に区別する |

## 書き方

- コード引用は最小限。該当する2〜5行のみ。
- 設計書の見出し名は補助。「〜の節に反する」で終わらせず、具体的に何が壊れるかまで書く。
- 項目が3つ以上あるなら、冒頭で共通する判断軸をまとめてから個別に入る。

## 適用対象外

- 事実の報告のみ（テスト件数・実行時間等）
- 既に合意済みの事項の再説明
- ユーザーが明示的に「要点だけでいい」と述べた場合
